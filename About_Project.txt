AshML — Kubernetes-Native GPU Machine Learning Infrastructure Platform
Master Project Specification / Engineering Reference
1. Project Overview
Project Name
AshML

Subtitle
A Kubernetes-native GPU machine learning infrastructure and orchestration platform powered by AshGPU and integrated with Ashcode.

2. Vision
AshML is a self-hosted, Kubernetes-native machine learning infrastructure platform designed to combine:

Machine Learning

ML Systems

Backend Engineering

Distributed Systems

GPU Infrastructure

Kubernetes

DevOps / Platform Engineering

Observability

Reliability Engineering

AI Developer Tooling

into one coherent engineering project.

The goal is not to build another generic AI application, chatbot, RAG application, or simple model-serving API.

The goal is to build a small but technically serious ML infrastructure platform, conceptually similar to a miniature internal ML cloud.

The platform should allow a developer to:

Register datasets and models.

Submit ML training jobs.

Request CPU/GPU/memory resources.

Schedule workloads onto available compute resources.

Execute workloads using Kubernetes.

Use AshGPU as the GPU execution/runtime layer where applicable.

Track experiments and training metrics.

Store checkpoints and model artifacts.

Register model versions.

Deploy trained models as inference services.

Route inference requests to model deployments.

Monitor infrastructure and ML workloads.

Detect workload failures.

Recover/reschedule failed workloads where possible.

Inspect logs, metrics, traces, scheduling decisions, and resource usage.

Interact with the platform through a CLI/API.

Eventually allow Ashcode to act as an AI-powered interface for operating the platform.

The final system should feel like a real infrastructure product, not a collection of disconnected demos.

3. Why This Project Exists
This project is intentionally designed to demonstrate competence across several engineering domains.

It should be strong enough to support applications for:

Backend Engineering

Distributed Systems Engineering

Infrastructure Engineering

DevOps / Platform Engineering

SRE

Kubernetes Engineering

ML Infrastructure / ML Platform Engineering

ML Systems Engineering

GPU Systems

Core ML Engineering

The key principle is:

One system should demonstrate multiple engineering disciplines naturally, rather than artificially combining unrelated technologies.

For example:

Kubernetes exists because workloads need orchestration.

The scheduler exists because ML workloads have specialized resource requirements.

AshGPU exists because GPU execution needs to be exposed to the platform.

The model registry exists because trained artifacts need lifecycle management.

Observability exists because distributed infrastructure needs visibility.

Ashcode exists because developers need a high-level interface to operate complex infrastructure.

Everything should have a reason.

10. Training Job Specification
A training job should be declarative.

Example:

apiVersion: ash.ai/v1
kind: TrainingJob

metadata:
  name: resnet-cifar

spec:
  image: ash/ml-pytorch:latest

  command:
    - python
    - train.py

  args:
    - --epochs
    - "50"

  resources:
    cpu: "8"
    memory: "32Gi"
    gpu: "2"

  dataset:
    name: cifar10
    version: v3

  output:
    model: resnet-cifar

  retryPolicy:
    maxRetries: 3
The exact schema may evolve.

The important principle is:

Users describe desired state, while the platform determines how to achieve it.

11. Scheduling System
The scheduler is one of the most important components of AshML.

Do not simply treat the scheduler as a thin wrapper around Kubernetes.

The project should eventually contain an ML-aware scheduling layer.

The scheduler should consider:

CPU availability

RAM availability

GPU availability

GPU memory

Number of GPUs

GPU type

Node availability

Resource quotas

Job priority

Queue state

Locality

Potentially GPU utilization

Potentially GPU topology

Potentially data locality

Example:

Training Job
    │
    ▼
Resource Requirements
    │
    ├── CPU: 8
    ├── RAM: 32 GB
    ├── GPU: 2
    └── GPU Memory: >= 16 GB
    │
    ▼
Scheduler
    │
    ├── Node A → insufficient GPU
    ├── Node B → 1 GPU available
    ├── Node C → 2 GPUs available
    └── Node D → unavailable
    │
    ▼
Node C selected
    │
    ▼
Kubernetes workload created

14. AshML Kubernetes Operator
One of the major milestones is building a Kubernetes Operator.

AshML should define custom resources such as:

apiVersion: ash.ai/v1
kind: TrainingJob

metadata:
  name: resnet-cifar

spec:
  replicas: 2

  resources:
    gpu: 2
    cpu: 8
    memory: 32Gi

  training:
    framework: pytorch
    script: train.py
The operator should:

Watch TrainingJob resources.

Validate specifications.

Determine required resources.

Interact with the scheduler.

Create necessary Kubernetes resources.

Monitor child resources.

Update job status.

Detect failures.

Retry when appropriate.

Handle completion.

Clean up temporary resources.

Persist useful status and metadata.

Eventually the operator should become responsible for maintaining the desired state of ML workloads.

22. Failure Recovery
Reliability is a major goal.

The system should deliberately support failure scenarios.

Training pod failure
training pod dies
      ↓
operator detects failure
      ↓
checkpoint discovered
      ↓
new pod created
      ↓
training resumes
GPU failure
GPU becomes unhealthy
      ↓
GPU marked unavailable
      ↓
scheduler stops assigning jobs
      ↓
recoverable workload rescheduled
Inference failure
inference pod crashes
      ↓
Kubernetes restarts pod
      ↓
readiness check
      ↓
traffic restored
Node failure
node disappears
      ↓
Kubernetes detects node failure
      ↓
workloads become unavailable
      ↓
controller/scheduler attempts recovery
Failure handling must be observable.

The platform should clearly communicate:

What failed
When it failed
Why it failed
What recovery action was taken
Whether recovery succeeded

43. Technology Philosophy
Use mature technologies where they make sense.

Do not reinvent infrastructure unnecessarily.

For example:

Kubernetes → orchestration
PostgreSQL → metadata/state
Redis → queues/caching where appropriate
S3-compatible storage → artifacts
Prometheus → metrics
Grafana → visualization
OpenTelemetry → tracing
Build custom components only where they demonstrate the project's core engineering value.

The most important custom components should be:

AshML Control Plane
AshML Scheduler
AshML Kubernetes Operator
AshGPU Integration
Ashcode Integration
44. Important Engineering Principle
Do not use technology merely because it looks impressive on a resume.

Every component must answer:

Why does this exist?

For example, do not add:

Kafka
RabbitMQ
Redis
NATS
gRPC
REST
GraphQL
just because they are popular.

Better:

REST
→ Public control-plane API

gRPC
→ Internal service communication where justified

Redis
→ Transient queue/cache where appropriate

PostgreSQL
→ Durable metadata/state

Object storage
→ Large artifacts

Kubernetes
→ Workload orchestration
Minimize unnecessary complexity.

53. What NOT to Do
Do not build a generic AI chatbot
The primary product is infrastructure.

Do not make RAG the main feature
RAG can be an example workload, but it is not the core project.

Do not make the frontend the project
The UI is secondary.

Do not use Kubernetes as decoration
Kubernetes must solve real orchestration problems.

Do not add microservices unnecessarily

Do not fake GPU functionality

Do not claim distributed ML without actually running distributed workloads
The project must demonstrate real behavior.

Do not optimize for technology count
Depth is more valuable than breadth.

55. Coding-Agent Instructions

56. Coding-Agent Rules
Rule 1 — Do not implement the entire specification at once
This document describes the long-term vision.

It does NOT mean every feature should be implemented immediately.

Always determine:

What is already implemented?
What is the current milestone?
What is the smallest correct implementation?
What dependencies does it have?
What existing code can be reused?
Rule 2 — Prefer incremental implementation
For every feature:

Design
 ↓
Small implementation
 ↓
Tests
 ↓
Integration
 ↓
Observability
 ↓
Documentation
Do not build huge amounts of untested code.

Rule 3 — Preserve architecture
Maintain the distinction between:

Control Plane
Compute Plane
Do not place arbitrary infrastructure logic inside ML training containers.

Rule 4 — Avoid unnecessary dependencies
Before introducing a dependency, ask:

Can the standard library solve this?

Does the dependency materially simplify the system?

Does it create operational complexity?

Is it mature and maintained?
Rule 5 — Do not fake functionality
Never implement fake GPU metrics, fake scheduling, fake distributed training, fake Kubernetes behavior, or fake performance numbers simply to make a demo work.

If functionality is unavailable, clearly identify it as:

TODO
Stub
Simulation
Mock
Future integration
A simulated GPU may be used for development, but it must be clearly separated from the real AshGPU path.
